# Project Instructions

## Project Name
**Simulity** — An autonomous sandbox simulation

## Core Vision
Build a highly extensible, data-driven 2D simulation system where NPCs can live autonomous background lives over long periods of time. The system must support runtime addition of new content (jobs, locations, needs, behaviors) and be deeply integrated with LLM agents via MCP tools.

The end goal is a living world where NPCs have needs, make decisions, form relationships, follow routines, and generate their own stories — even when the player is not directly interacting with them.

The player participates inside this world as a **PC (Player Character)**. When the PC initiates roleplay interaction with one or more NPCs (conversation, actions, social scenes), an LLM assumes control of those specific NPCs for the duration of the scene. The LLM receives the complete authoritative state generated by the simulation (current needs, mood, recent history, relationships, knowledge, desires). All non-involved NPCs continue running their autonomous simulation systems without interruption. When the player interaction concludes, control of the involved NPC(s) returns to the autonomous layer, with any resulting state changes reconciled back through validated channels.

## Core Principles (Non-Negotiable)

- **Data-Driven First**: Almost everything should be definable through data/configs rather than hardcoded in TypeScript. This includes Needs, Jobs, Tasks, Locations, and Behaviors.
- **Runtime Extensibility**: New jobs, locations, needs, and behaviors should be addable while the simulation is running (via MCP tools / LLM).
- **Visual Editing from the Start**: Behavior Trees must be editable visually. This is a first-class requirement, not a later feature.
- **Hybrid Decision Making**: Use a layered approach — Utility AI (or similar) for goal selection + Behavior Trees for execution.
- **Hybrid Autonomous Simulation + LLM Roleplay**: Autonomous Utility + Behavior Tree systems govern all NPC behavior when the player is not directly engaged. LLM roleplay activates selectively and only for player-involved NPCs. The LLM operates on read-only snapshots of simulation state (via Blackboard and event history) and returns structured state deltas for reconciliation by the autonomous layer. The autonomous systems remain the single source of truth for background activity and long-term world state.
- **Server is the Single Source of Truth**: The frontend is a thin client/view layer only. All simulation logic lives on the backend.
- **LLM / MCP Integration**: The system must expose clean, well-defined MCP tools for two purposes: (1) creation and modification of world content (jobs, locations, characters, behaviors, needs) at runtime, and (2) runtime roleplay of specific NPCs during player interactions, with the LLM consuming authoritative Blackboard snapshots and history.
- **Staged / Hierarchical Navigation**: NPCs should be able to navigate realistically across multiple scales (city → building → interior) using entrances as containers.
- **Start Simple, Design for Growth**: Begin with stylized/simple implementations, but the architecture must support increasing complexity over time without major rewrites.

## Working Methodology

- We will work primarily through **strong specification documents**. High-level thinking and architecture happens here. Implementation details are handed off via clear specs.
- All major architectural decisions should be captured in the Architecture Foundations document and updated as we learn.
- We prioritize **clarity and maintainability** over premature optimization.
- We will regularly revisit whether current systems are still aligned with the "data-driven + runtime extensible" principle.

## Current Focus Areas (Phase 1)

1. Foundational data models (Needs, Jobs, Locations, Behavior Tree definitions)
2. Goal Selection layer (Utility AI or equivalent)
3. Data-driven Behavior Tree system + Visual Editor integration
4. Basic world generation (roads first, then buildings as containers)
5. Navigation system that supports staged movement across scales
6. Blackboard system as the central state container for NPCs (including requirements for clean LLM-consumable snapshots and state reconciliation)

## Non-Goals (For Now)

- High-fidelity visuals or complex 3D
- Full persistence and save/load system (until core simulation is stable)
- Complex relationship / social simulation in the autonomous layer (this comes after basic autonomy works; nuanced social roleplay during player interactions is handled by the LLM layer)
- Performance optimization for very large populations (focus on correctness and extensibility first)
- LLM directly mutating simulation state or bypassing the defined Blackboard hand-off and validation protocol

## Success Criteria for Early Phases

- We can define new jobs and behaviors through data (without code changes)
- An NPC can pursue a goal selected by the Utility layer and execute it via a Behavior Tree
- Basic city generation + navigation works (roads → buildings as containers)
- The visual Behavior Tree editor can create and modify trees that actually run in the simulation
- New content can be added via MCP tools while the simulation is running
- Clean hand-off protocol exists: when a player interacts with NPC(s), the LLM receives full simulation context for those NPCs, non-involved NPCs continue uninterrupted, and resulting state is correctly reconciled back into the autonomous systems when the interaction ends

## Collaboration Notes

- Be direct and precise. Avoid vague language in specifications.
- When handing work to agents, include clear constraints, non-goals, and acceptance criteria.
- Regularly challenge whether we are staying true to the data-driven and extensibility principles.
